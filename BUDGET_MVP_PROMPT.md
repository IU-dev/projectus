## Цель

Заменить заглушку раздела «Бюджет» рабочим MVP для:

- планирования сметы проекта;
- контроля лимитов на уровне строки, подстатьи и крупной статьи;
- версионирования и согласования изменений/переносов;
- регистрации поступлений средств;
- создания, согласования и исполнения платежных поручений;
- независимого назначения всех финансовых полномочий участникам проекта.

Приоритеты: корректность денежных расчетов и прав доступа, транзакционная защита от превышений, компактный табличный интерфейс. Не усложняй MVP возможностями из раздела «Вне объема».

## Принятые продуктовые решения

Эти решения считаются окончательными для MVP; не останавливайся для их повторного согласования.

### 1. Права

Сохрани существующие коды `VIEW_FINANCE`, `EDIT_BUDGET`, `PREPARE_PAYMENTS`, `APPROVE_PAYMENTS`. Уточни русские подписи при необходимости и добавь отдельные права:

- `APPROVE_BUDGET_CHANGES` — согласовывать изменения сметы и переносы;
- `EXECUTE_PAYMENTS` — исполнять согласованные платежи;
- `RECORD_RECEIPTS` — отражать поступления средств.

Права независимы. Пользователь может открыть финансовый раздел, если имеет `VIEW_FINANCE` или хотя бы одно финансовое действие, но сервер возвращает и разрешает только доступные ему действия. Одно право не должно неявно давать другое. Владелец проекта, как и сейчас, имеет все проектные права.

В финансовых настройках проекта храни:

- конкретный список пользователей, каждый из которых должен согласовать любой платеж проекта;
- `require_payment_bank_details`, по умолчанию `True`: обязательны ли расчетный счет и полные банковские реквизиты получателя для отправки заявки и исполнения платежа.

Для списка используй отдельную модель настройки наподобие `ProjectPaymentApprover(project, user, position)` с уникальностью пары project/user. Выбирать можно владельца проекта и его действующих участников; каждый выбранный человек должен иметь `APPROVE_PAYMENTS` (у владельца оно есть автоматически). Список не может быть пустым при отправке платежа. Менять настройки может владелец или пользователь с `EDIT_BUDGET`.

При отправке платежа скопируй текущий список конкретных согласующих в строки согласования самого платежа, а обязательность банковских реквизитов — в поле платежа. Последующие изменения настроек не меняют уже отправленные платежи. Все зафиксированные согласующие должны одобрить платеж; автор может входить в их число. Любой отказ немедленно переводит платеж в статус «Отклонен». Пользователь с `APPROVE_PAYMENTS`, который не входит в зафиксированный список данного платежа, не может голосовать по нему.

### 2. Шаблоны статей

Администратор системы создает шаблоны через Django admin. Для MVP отдельный пользовательский интерфейс и новое системное право для шаблонов не нужны.

Добавь `BudgetTemplate` и иерархические элементы шаблона. В шаблоне не больше двух уровней: крупная статья и необязательная подстатья. Шаблон активен/неактивен, имеет название, а элементы — название, необязательное пояснение и порядок. Применение шаблона копирует только крупные статьи и подстатьи в пустую исходную смету. Конкретные строки сметы никогда не входят в шаблон и всегда создаются в проекте вручную. Крупные статьи и подстатьи также можно создать вручную.

Зарегистрируй шаблоны в Django admin с компактным редактированием структуры, насколько это разумно без сторонних зависимостей.

### 3. Версии сметы

Реализуй явные версии сметы:

- `BudgetRevision`: проект, последовательный номер внутри проекта, вид (`initial`, `amendment`, `transfer`), статус (`draft`, `pending`, `active`, `rejected`, `superseded`), ссылка на базовую версию, обязательная причина для amendment/transfer, автор, согласующий, даты создания/отправки/решения;
- `BudgetSection`: версия, стабильный UUID `key`, название, необязательное пояснение, порядок, родитель; разрешены только крупная статья без родителя и подстатья с родителем верхнего уровня;
- `BudgetLine`: версия, стабильный UUID `key`, статья/подстатья, наименование расхода, необязательные `unit_price`, `quantity` и `unit_name`, обязательные `total_amount`, `cofinancing_amount`, `requested_amount`, необязательный развернутый комментарий и порядок.

Строка может относиться либо к подстатье, либо непосредственно к крупной статье, если у нее нет подстатей. Не допускай одновременное смешение прямых строк и подстатей внутри одной крупной статьи. `unit_price` и `quantity` разрешены только парой; единица измерения обязательна при наличии количества. Если цена и количество заданы, `total_amount` должна равняться их произведению с округлением до копеек. Всегда выполняется `total_amount = cofinancing_amount + requested_amount`; обе составляющие неотрицательны, общая стоимость положительна. Это соответствует реальному образцу, включая строки без цены/количества и строки с нулевой запрашиваемой суммой.

Стабильные `key` сохраняются при клонировании версии. Они нужны для учета платежей по одной логической строке между версиями.

При первом открытии бюджета создай ровно одну пустую исходную draft-версию. Ее можно заполнить вручную или применить один шаблон, пока смета пуста. Редактор с `EDIT_BUDGET` публикует исходную версию сразу как active; отдельное согласование исходной версии не требуется. После публикации active-версия неизменяема.

Любое последующее изменение создается только через полное клонирование active-версии в новый draft:

- `amendment` может менять общий плановый бюджет;
- `transfer` должен сохранять общий итог проекта, содержать хотя бы одно уменьшение и одно увеличение и иметь ненулевые изменения;
- draft редактирует пользователь с `EDIT_BUDGET`, затем отправляет на согласование;
- approve/reject выполняет пользователь с `APPROVE_BUDGET_CHANGES`;
- при approve прежняя active становится superseded, новая — active;
- одновременно допускается не более одного draft/pending изменения проекта;
- нельзя согласовать версию, если новый лимит любой логической строки ниже уже зарезервированных и исполненных платежей по этой строке;
- rejected и все опубликованные версии неизменяемы; история доступна для просмотра.

Плановые суммы крупной статьи и подстатьи не храни отдельно: это суммы дочерних строк. На каждом уровне вычисляй общую стоимость, софинансирование и запрашиваемую сумму. Для исполнения также показывай согласовано к оплате, исполнено и остаток от общей стоимости. Платежи контролируй именно по `total_amount`: денежные поступления отдельно ограничат реально доступные средства. Контроль строки автоматически гарантирует непревышение агрегатов, но агрегаты все равно должны явно отображаться и проверяться тестом.

Не разрешай удалять из новой версии логическую строку, по которой есть согласованный или исполненный платеж. Строку без таких платежей удалить можно в draft.

### 4. Поступления и доступные средства

Добавь операцию `FundReceipt`: проект, положительная сумма, дата поступления, назначение/комментарий, автор и дата создания. Создавать ее может только `RECORD_RECEIPTS`, просматривать — любой пользователь с финансовым доступом. В MVP поступления неизменяемы и не удаляются; исправление делается новой компенсирующей операцией с понятным комментарием (разреши положительную сумму только, поэтому ошибку отражай отдельным корректирующим поступлением в будущем; сейчас в UI просто предупреди об неизменяемости).

Показывай две суммы:

- остаток на счете = все поступления − исполненные платежи;
- доступно для новых согласований = все поступления − исполненные платежи − уже согласованные, но еще не исполненные платежи.

### 5. Платежные поручения

Добавь:

- `PaymentOrder`: последовательный внутренний номер заявки внутри проекта, проект, стабильный `budget_line_key`, снимки названия строки и пути статьи для истории, сумма, описание/обоснование заявки от создателя, статус (`draft`, `pending`, `approved`, `rejected`, `executed`), автор, снимок настройки обязательности банковских реквизитов, даты отправки/согласования/исполнения, исполнитель;
- реквизиты получателя прямо в `PaymentOrder`: тип с кодами `fl`, `ip`, `org`, полное имя/наименование, ИНН, необязательный КПП, расчетный счет, наименование банка, БИК и корреспондентский счет. Отдельный справочник контрагентов в MVP не нужен; после отправки эти поля становятся историческим снимком;
- поля, которые заполняет только исполнитель в момент исполнения: `payment_document_date`, `payment_document_number` (строка, не число) и `payment_purpose` — точное назначение платежа для банка/финансового отчета;
- связь many-to-many с `ProjectEvent`: мероприятия необязательны, но все выбранные мероприятия обязаны принадлежать тому же проекту;
- `PaymentApproval`: платеж, конкретный обязательный согласующий, состояние `pending`/`approved`/`rejected`, необязательный комментарий и дата решения; по одной строке на каждого согласующего, уникальность payment/approver;
- `PaymentAttachment`: платеж, приватный файл, исходное безопасное имя, размер, загрузивший, дата. Это связь один-ко-многим: к одному платежу можно последовательно прикрепить любое количество файлов, а не только один.

Получатель обязателен для каждого платежа, включая проекты с необязательными банковскими реквизитами. Нормализуй пробелы в цифровых реквизитах и валидируй российские форматы без проверки контрольных цифр: ИНН физлица/ИП — 12 цифр, ИНН юридического лица — 10 цифр, КПП юридического лица — 9 цифр и обязателен только для него, БИК — 9 цифр, расчетный и корреспондентский счета — по 20 цифр. Для физлица и ИП КПП должен быть пустым. Когда `bank_details_required=True`, расчетный счет, банк, БИК и корреспондентский счет обязательны уже при отправке заявки и повторно проверяются при исполнении. Когда `False`, эти четыре поля можно оставить пустыми или заполнить полностью/частично: это режим устного согласования либо учета уже проведенных оплат. Тип, имя и ИНН получателя остаются обязательными в обоих режимах.

Сценарий:

1. Пользователь с `PREPARE_PAYMENTS` создает draft, выбирает строку текущей active-сметы, сумму, описывает основание заявки, указывает тип, имя и налоговые реквизиты получателя, при необходимости вводит его банковские реквизиты, выбирает связанные мероприятия, прикладывает файлы и отправляет на согласование. Он не может заполнять дату/номер платежного документа и точное банковское назначение платежа.
2. После отправки содержимое платежа неизменяемо. Draft может удалить только его автор до отправки; финансовые записи других статусов физически не удаляй.
3. Зафиксированный согласующий с `APPROVE_PAYMENTS` approve/reject свою pending-строку. Повторное решение запрещено. Только когда все зафиксированные согласующие одобрили платеж, он становится approved и резервирует деньги и лимит строки. Любой reject завершает процесс отклонением.
4. Пользователь с `EXECUTE_PAYMENTS` исполняет только approved-платеж. В форме исполнения он обязательно указывает дату и номер платежного документа, а также точное «Назначение платежа». Дата не может быть в будущем. Если снимок настройки требует банковские реквизиты, повторно проверь их полноту. Исполнение требует хотя бы одного прикрепленного файла и переводит платеж в executed с фиксацией пользователя и времени. Повторное исполнение идемпотентно и не создает двойного расхода.
5. Несколько файлов можно последовательно добавлять на любой стадии пользователем, который имеет право действия на этой стадии: автор с `PREPARE_PAYMENTS` для draft/pending, только зафиксированный согласующий с `APPROVE_PAYMENTS` для pending, исполнитель с `EXECUTE_PAYMENTS` для approved/executed. Удаление разреши только автору файла в draft; после отправки вложения неизменяемы. Максимальный размер одного файла — 20 МБ, общего ограничения количества в MVP нет.

На каждом approve пересчитывай состояние. На финальном approve в одной `transaction.atomic()` заблокируй строку сериализации проекта (`Project.objects.select_for_update()` достаточно) и проверь одновременно:

- доступный остаток с учетом уже зарезервированных approved-платежей не меньше суммы;
- остаток строки active-сметы с учетом approved и executed платежей по тому же `budget_line_key` не меньше суммы;
- active-версия все еще содержит эту логическую строку.

Если проверка не проходит, не записывай голос и оставляй платеж pending с понятной ошибкой. При исполнении снова используй блокировку и защитную проверку. Суммы draft/pending не резервируют лимиты. Rejected не учитывается нигде.

Все выборки строк, платежей, мероприятий, вложений и действий жестко ограничивай текущим проектом. Защити от подмены ID/UUID и гонок. Важные переходы статусов размести в `core/budget_services.py`, а не размазывай по views/forms.

### 6. Аудит

Пиши `AuditEvent` минимум для:

- публикации исходной сметы;
- создания, отправки, согласования и отклонения новой версии;
- создания поступления;
- создания и отправки платежа;
- каждого approve/reject;
- исполнения платежа;
- добавления вложения.

В `details` не сохраняй содержимое файлов, банковские счета, БИК, ИНН/КПП и лишние персональные данные. Суммы сериализуй строкой, не float.

## Интерфейс

Заменить `ProjectSectionView` для бюджета на отдельные Vue-страницы и добавить их в `frontend/pages.js`/sidebar.

Главная страница бюджета должна быть компактной и преимущественно табличной:

- вверху одна узкая строка показателей: общая стоимость сметы, запрашиваемая сумма, софинансирование, поступило, зарезервировано, исполнено, доступно;
- простые вкладки/ссылки: «Смета», «Платежи», «Поступления», «История сметы»;
- смета — одна иерархическая таблица: крупная статья → необязательная подстатья → строка. Для строки показывай наименование, цену/количество компактной второй строкой, общую стоимость, софинансирование, запрашиваемую сумму, согласовано, исполнено, остаток и компактные действия; для разделов — агрегированные итоги;
- платежи — таблица с внутренним номером заявки, получателем, описанием заявки/назначением после исполнения, строкой сметы, суммой, статусом, прогрессом вида «согласовано N из M конкретных согласующих» и действиями;
- поступления — таблица с датой, суммой, назначением и автором;
- платеж — отдельная компактная страница с реквизитами получателя, связанными мероприятиями, согласованиями, файлами и доступными действиями. После исполнения отдельно показывай дату и номер платежного документа и точное назначение платежа;
- настройки бюджета — компактная форма выбора конкретных согласующих из владельца и участников проекта и переключателя «Требовать банковские реквизиты для проведения платежа» с коротким пояснением двух режимов. Рядом с выбранным человеком показывай отсутствие `APPROVE_PAYMENTS` как ошибку настройки, а не выдавай право автоматически.

Не создавай сетку крупных карточек, графики, drag-and-drop, модальные окна или новый дизайн-системный слой. Переиспользуй `.panel`, `.table-wrap`, `.button`, `.tag`, существующие токены и мобильные правила. На узком экране таблицы могут иметь горизонтальный скролл; действия должны оставаться доступными. Все русские подписи и сообщения должны быть понятными бухгалтеру/менеджеру без технических терминов.

Сделай отдельные routes/views/forms для операций вместо одного универсального POST с параметром action. Используй существующую JSON/HTML схему. Обнови `core/frontend.py` явной сериализацией; модели Django или произвольные объекты в JSON не отдавай.

## Ожидаемая структура реализации

Имена можно слегка адаптировать под текущие соглашения, но разделение ответственности сохрани:

- модели и constraints в `core/models.py`;
- `core/budget_forms.py`;
- `core/budget_services.py` для клонирования/публикации/согласования и финансовых проверок;
- `core/budget_views.py`;
- маршруты в `config/urls.py`;
- сериализация в `core/frontend.py`;
- HTML fallback templates;
- `BudgetView.vue`, страница платежа и при необходимости одна страница редактора версии;
- обновление `frontend/pages.js`, `ProjectSidebar.vue`, общих стилей только по необходимости;
- миграция, Django admin и сфокусированные тесты.

Избегай N+1: списки загружай через `select_related`/`prefetch_related`, агрегаты считай ограниченным числом запросов. Не добавляй сторонние зависимости.

## Минимальные тесты и проверки

Не пиши исчерпывающий набор. Создай один сфокусированный `core/test_budget.py` примерно на 8–12 тестовых методов, покрывающих главные риски:

- независимость и отзыв финансовых прав; отсутствие доступа у системного сотрудника/superuser к чужому проекту;
- создание исходной сметы вручную/из шаблона, валидация `total_amount = cofinancing_amount + requested_amount`, публикация и вычисление трех разрезов итогов на всех уровнях;
- amendment/transfer, запрет изменения итоговой суммы transfer и запрет снижения лимита ниже резерва;
- поступления, согласование всеми конкретно настроенными людьми, запрет голоса постороннего пользователя, неизменность списка для уже отправленного платежа и недопустимый повторный голос;
- запрет согласования при нехватке средств или лимита строки, включая два последовательных платежа;
- валидация ИНН/КПП/счетов/БИК и оба режима обязательности банковских реквизитов;
- запрет создателю задавать реквизиты исполнения; обязательные дата, номер документа, точное назначение и файл при исполнении; отсутствие двойного списания;
- защита от чужих строк/мероприятий/файлов и закрытая загрузка файла;
- хотя бы одна проверка CSRF для финансовой мутации.

После реализации запусти только релевантные проверки:

```sh
DEBUG=1 USE_SQLITE=1 .venv/bin/python manage.py check
DEBUG=1 USE_SQLITE=1 .venv/bin/python manage.py makemigrations --check --dry-run
DEBUG=1 USE_SQLITE=1 .venv/bin/python manage.py test core.test_budget core.test_frontend
npm test
npm run build
```

Если изменение общей сериализации ломает существующий event-модуль, дополнительно запусти `core.test_events`. Полный browser/E2E прогон не обязателен. Не трать время на скриншоты; пользователь вручную проверит тонкости интерфейса.

## Вне объема MVP

Не реализовывай сейчас:

- интеграции с банками, импорт выписок и реальную отправку платежа в банк;
- несколько валют, курсы и НДС;
- частичное исполнение одного платежа;
- возвраты, отрицательные поступления и бухгалтерские проводки;
- договоры, электронную подпись и автоматическую связь с будущим модулем договоров;
- уведомления, email, экспорт Excel/PDF, печатные формы;
- автоматическую генерацию финансового отчета фонда и отчетные периоды;
- произвольные маршруты и последовательный порядок согласования, персональное назначение согласующих для отдельного платежа;
- разные списки согласующих в зависимости от статьи/подстатьи/строки сметы — это следующий этап после MVP;
- массовые операции и сложную аналитику.

## Критерий готовности

Задача завершена, когда пользователь с соответствующими независимыми правами может создать/опубликовать смету, зарегистрировать поступление, создать платеж по строке с получателем и требуемыми проектом реквизитами, получить одобрение каждого конкретного согласующего из зафиксированного списка и исполнить его, указав дату/номер платежного документа, точное назначение и приложив хотя бы один из поддерживаемых нескольких файлов; ни лимит строки, ни агрегаты сметы, ни доступный остаток не могут быть превышены даже последовательными конкурентными действиями; изменения и переносы проходят через неизменяемую новую версию; история и аудит сохраняются; JSON и HTML fallback работают; указанные проверки проходят.

В финальном ответе перечисли только реализованное, выполненные проверки и оставшиеся реальные ограничения/ручные проверки. Не пересказывай это ТЗ и не предлагай новую фазу проектирования.

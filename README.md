# Projectus

Первый этап SaaS-сервиса для социальных и других проектов: учетные записи, заявки на создание проектов и индивидуальный доступ.

Стек: Python 3.13, Django 5.2 LTS, PostgreSQL, Vue 3. Интерфейс собран Vite, вход по email с серверными сессиями Django.

## Что реализовано

- Публичный лендинг на `/` для гостей: описание Projectus, преимущества, порядок начала работы и ссылки на регистрацию и вход. После входа этот же адрес открывает личный кабинет.

- Открытая регистрация, подтверждение email с одноразовой ссылкой на 24 часа.
- Вход и выход, восстановление и смена пароля. Минимальная длина пароля — 10 символов.
- Ограничение частоты входа, регистрации и отправки писем с хранением счетчиков в БД.
- Пользователь подает **заявку на создание проекта**. До одобрения сотрудником Projectus самого проекта нет.
- Одобрение или отклонение заявки; отклонение требует комментария. Повторное рассмотрение не создает второй проект.
- Владелец проекта — пользователь, подавший заявку. Только он управляет участниками и их доступом.
- Приглашения по email только уже зарегистрированным пользователям, действующие 7 дней. Получателю нужно подтвердить тот же email и принять приглашение. Можно отозвать приглашение.
- Индивидуальные разрешения участников, изменение и отзыв доступа без фиксированных проектных ролей.
- Главный аккаунт выдает сотрудникам отдельные системные полномочия. Сотрудники не могут выдавать полномочия другим сотрудникам.
- Журнал регистрации, подтверждения email, решений по заявкам, приглашений и изменений доступа.
- Адаптивный русскоязычный интерфейс, CSRF-защита и серверные проверки разрешений.
- Подготовлен раздел «Мои договоры» (`/contracts/`), доступный пользователю независимо от участия в проектах. Пока он показывает пустое состояние; модель и работа с договорами относятся к следующему этапу.

## Правила доступа

В проекте владелец имеет полный доступ. Другой пользователь получает доступ к общей карточке после принятия приглашения. Остальные действия разрешены только при наличии соответствующего флажка.

Каталог `core/permissions.py` содержит разрешения для мероприятий, финансов, договоров и грантов. Из этих действий на первом этапе реализовано только изменение сведений проекта (`edit_project`). Остальные разрешения сохраняются как основа для следующих модулей; самих модулей еще нет. Подготовка платежей и согласование платежей — разные полномочия. Юридически значимое электронное подписание пока не реализовано.

Системные полномочия:

| Код | Возможность |
| --- | --- |
| `view_requests` | Просмотр заявок на создание проектов |
| `approve_projects` | Просмотр, одобрение и отклонение заявок |
| `view_users` | Просмотр учетных записей |
| `view_audit` | Просмотр журнала действий |

Главный аккаунт создается командой `createsuperuser`, имеет все системные полномочия и управляет их назначением. Даже главный аккаунт не получает автоматический доступ к клиентским проектам. Журнал содержит email и технические сведения действий, поэтому доступ к нему выдается отдельно.

Стандартная Django admin показывает главному аккаунту пользователей только для чтения. Основное управление сервисом находится в `/operations/`.

В «Полномочиях сотрудников» выберите существующего пользователя через поиск: минимум 3 символа имени, фамилии или email (он же логин). Поиск показывает до 10 активных пользователей с подтвержденным email. После выбора загружаются текущие полномочия; сохранение заменяет их, а пустой набор отзывает все назначения. Эта операция доступна только главному аккаунту.

## Локальный запуск с PostgreSQL

Перед запуском Django соберите фронтенд (Node.js 22 и npm):

```sh
npm ci
npm run build
```

Сборка помещается в `static/frontend/`; Vue загружается локально, без CDN. При изменении Vue-компонентов запускайте `npm run watch` в отдельном терминале. Приложение открывается через Django на порту 8000, отдельный сервер фронтенда не нужен.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
```

Отредактируйте `.env`: задайте собственные `SECRET_KEY` и `POSTGRES_PASSWORD`. `.env` не загружается автоматически; перед командами Django экспортируйте переменные в текущий терминал:

```sh
set -a
source .env
set +a
docker compose up -d db
.venv/bin/python manage.py migrate
.venv/bin/python manage.py createsuperuser
.venv/bin/python manage.py runserver 127.0.0.1:8000
```

Откройте http://127.0.0.1:8000/. В режиме разработки письма выводятся в терминал сервера. Для подтверждения email откройте ссылку из письма и нажмите кнопку подтверждения на странице.

Первый сценарий:

1. Создайте обычный аккаунт через `/register/`, подтвердите email и войдите.
2. Подайте заявку на проект.
3. В отдельной сессии войдите главным аккаунтом, откройте «Управление сервисом → Заявки на проекты» и одобрите заявку.
4. Владелец увидит проект в своем кабинете и сможет пригласить участников с нужными правами.
5. Для сотрудника зарегистрируйте и подтвердите обычный аккаунт; главный аккаунт назначит ему полномочия на странице «Полномочия сотрудников».

В репозитории нет предустановленных пользователей и паролей.

## Быстрая проверка без PostgreSQL

SQLite поддерживается только для локальной разработки и быстрых тестов:

```sh
DEBUG=1 USE_SQLITE=1 .venv/bin/python manage.py migrate
DEBUG=1 USE_SQLITE=1 .venv/bin/python manage.py test
DEBUG=1 USE_SQLITE=1 .venv/bin/python manage.py runserver 127.0.0.1:8000
```

Тесты проверяют подтверждение email, смену пароля и инвалидирование сессии, индивидуальные разрешения, изоляцию проектов, невозможность одобрить заявку без полномочия, одноразовые приглашения, отзыв доступа, CSRF и экранирование HTML.

Дополнительные проверки фронтенда:

```sh
npm test
npx playwright install chromium
DEBUG=1 USE_SQLITE=1 PROJECTUS_BROWSER_TESTS=1 .venv/bin/python manage.py test
```

Браузерный тест запускает временный Django-сервер на свободном порту и использует отдельную тестовую БД. Он проверяет регистрацию, подтверждение email, вход/выход, заявку и одобрение проекта, редактирование, приглашение, выдачу и отзыв прав, системные полномочия и смену пароля. Без `PROJECTUS_BROWSER_TESTS=1` браузерный тест пропускается; серверные тесты выполняются всегда.

## Vue и JSON API

Структура Vue-компонентов и порядок добавления новой страницы описаны в [frontend/README.md](frontend/README.md). `App.vue` содержит оболочку, страницы вынесены в `frontend/views/`, реестр страниц — в `frontend/pages.js`, навигация — в `frontend/composables/`.

Публичные маршруты и ссылки из писем сохранены. Обычный GET возвращает оболочку Vue с безопасно сериализованными начальными данными. Django-шаблоны остаются резервным интерфейсом для браузеров с отключенным JavaScript; Django admin сохраняет штатный интерфейс.

На тех же маршрутах запрос с `Accept: application/json` возвращает JSON. GET получает данные страницы, POST выполняет действие; тело POST — `application/x-www-form-urlencoded`, повторяющиеся ключи `permissions` передают набор прав. JSON-тело POST не поддерживается. Пустой набор прав отзывает все права. Клиент использует `credentials: same-origin` и `X-CSRFToken` из ответа сервера. Токен обновляется после входа. Все действия проходят существующие Django-формы, проверки прав и ограничения частоты запросов.

- Страница: `{page, data, user, show_operations, csrf_token, messages}`. `data.form` содержит поля, варианты выбора и ошибки; пароль никогда не возвращается в значении поля.
- Успешное действие: `{redirect, user, show_operations, csrf_token, messages}`. `redirect` содержит адрес следующей страницы; JSON-клиент открывает его отдельным GET.
- Ошибка формы: HTTP 422 с данными страницы и ошибками полей.
- Требуется вход: GET возвращает HTTP 401 и адрес входа с `next`.
- Нет прав, объект недоступен, неверный метод или превышен лимит: HTTP 403/404/405/429 с `{error}`. Недоступное приглашение возвращает HTTP 410 с пояснением страницы.

Персональные ответы имеют `Cache-Control: no-store` и `Vary: Accept, Cookie`. Список полей JSON задан явно в `core/frontend.py`; пароли, nonce подтверждения и внутренние поля пользователей не сериализуются. Интерфейс отображает пользовательский текст через экранируемые привязки Vue.

Для проверки именно PostgreSQL запустите `manage.py test` без `USE_SQLITE`. Пользователь тестовой БД должен иметь право `CREATEDB`. SQLite не проверяет поведение блокировок PostgreSQL и параллельных транзакций; проверка на PostgreSQL обязательна перед выпуском.

## Публикация

Приложение пока не развернуто на публичном сервере. Для запуска в эксплуатации нужны:

- PostgreSQL и проверенные резервные копии.
- Случайный секрет, `DEBUG=0`, реальные `ALLOWED_HOSTS` и `PUBLIC_BASE_URL=https://...`.
- SMTP: `EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend`, `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `DEFAULT_FROM_EMAIL`, `EMAIL_USE_TLS`.
- HTTPS и WSGI-сервер для `config.wsgi:application`; `runserver` предназначен только для разработки.
- Раздача файлов из `STATIC_ROOT` после `manage.py collectstatic`, журналирование ошибок и мониторинг доставки писем.
- `npm ci && npm run build` перед `collectstatic`; Node.js нужен только при сборке.
- `manage.py check --deploy` и полный прогон тестов с PostgreSQL.

Если HTTPS завершает обратный прокси, настройку доверия прокси нужно добавить под конкретную инфраструктуру. По умолчанию заголовки `X-Forwarded-*` не используются для определения отправителя или формирования ссылок. Прокси должен передавать корректный клиентский адрес для ограничения частоты запросов.

Оплата, мероприятия, сметы, платежи, договоры, подписи и грантовые заявки относятся к следующим этапам. Одобрение проекта пока не связано с учетом оплаты.

## Структура

- `config/` — настройки, маршруты и WSGI.
- `core/models.py` — пользователи, заявки, проекты, участники, права, приглашения и журнал.
- `core/permissions.py` — каталог и проверки разрешений.
- `core/services.py` — транзакционные операции и отправка подтверждения email.
- `core/views.py` — пользовательские и административные сценарии.
- `core/frontend.py` — JSON-представление страниц и оболочка Vue поверх существующих обработчиков.
- `core/tests.py`, `core/test_frontend.py`, `core/test_browser.py` — серверные и браузерные проверки.
- `frontend/` — Vue-компоненты, клиент API и тесты; `vite.config.js`, `package-lock.json` — воспроизводимая сборка.
- `templates/`, `static/` — оболочка, резервный интерфейс, письма, стили и собранный фронтенд.

Django 5.2 выбран как [LTS-релиз](https://docs.djangoproject.com/en/5.2/releases/5.2/).

## Имена моделей доступа

- `ProjectMember` — участие пользователя в проекте.
- `ProjectMemberPermissions` — отдельное разрешение участника.
- `SystemPermissions` — отдельное системное полномочие пользователя.
- `ProjectMemberInvitations` — приглашение в проект.

Миграция `0001_initial` сразу создает модели с этими названиями. Отдельной миграции переименования нет.

Backend проверяет регистрацию получателя без учета регистра email, в том числе при прямом обращении к JSON API. Если учетной записи нет, приглашение не создается и письмо не отправляется. Ранее выданные приглашения сохраняются до истечения срока или отзыва; повторная отправка требует регистрации. Задача отмечена выполненной в [BACKLOG.md](BACKLOG.md).

### Мероприятия и приватные вложения

Права на создание/изменение плана, внесение факта и подтверждение выдаются участникам отдельно. В показатели проекта входят только факты подтверждённых мероприятий. Подтверждённые мероприятия и их вложения доступны только для чтения.

Загруженные материалы хранятся в `private_uploads/` (`MEDIA_ROOT`), до 20 МБ на файл. Этот каталог не должен раздаваться публично веб-сервером: скачивание выполняется через защищённые маршруты Django. Включайте каталог вложений вместе с БД в резервное копирование. Для production задайте подходящие лимиты загрузки на reverse proxy.

# Контекст разработки Projectus

Этот файл переносит решения и состояние проекта из обсуждения в Codex в новый чат, в том числе в PyCharm. Это резюме, а не полный текст переписки. Актуальный код нужно сверять перед изменениями.

## Продукт

Projectus — web SaaS для реализации социальных и других проектов. Пользователи регистрируются, создают проекты после одобрения Projectus, приглашают участников и ведут исполнение.

Планируемые модули:

- Мероприятия: Гант, планирование и занятость ресурсов.
- Финансы: смета, статьи и лимиты, планирование, учет и согласование платежей.
- Договорные отношения: связь ресурсов и финансов, договоры с исполнителями, электронное подписание договоров и актов.
- Учет заявок на гранты и другие меры поддержки.

Монетизация — оплата за каждый создаваемый и ведущийся проект. Сначала вручную, затем через платежные сервисы. Учет оплаты еще не реализован.

## Подтвержденные требования пользователя

- Стек backend: Python, Django, PostgreSQL.
- Фронтенд на Vue 3 с локальной сборкой Vite. Django-шаблоны сохранены как резервный интерфейс без JavaScript.
- Открытая регистрация.
- Владельцем проекта всегда является пользователь.
- Фиксированных ролей в проекте, кроме владельца, нет. Владелец индивидуально назначает участникам разрешенные действия.
- В Projectus главный аккаунт назначает сотрудникам конкретные системные полномочия, без фиксированных служебных ролей.
- Проект нельзя создать без одобрения администратора. Сейчас пользователь подает отдельную заявку, при одобрении создается проект.
- Приглашения разрешены только уже зарегистрированным пользователям. Проверка email без учета регистра реализована в общей Django-форме для HTML и JSON API.
- Пользователь попросил перечислить сущности и поля для дальнейшего сокращения. Конкретные удаления полей пока НЕ согласованы. Не удалять поля только на основании ранее предложенных вариантов упрощения.

## Обязательные названия моделей

- `User`
- `ProjectRequest`
- `Project`
- `ProjectMember` (бывшая Membership)
- `ProjectMemberPermissions` (бывшая ProjectGrant)
- `SystemPermissions` (бывшая SystemGrant)
- `ProjectMemberInvitations` (бывшая Invitation)
- `AuditEvent`
- `RateLimit`

Пользователь явно потребовал, чтобы начальная миграция сразу создавала модели под правильными названиями. В `core/migrations/` есть только `0001_initial.py` и `__init__.py`; отдельная миграция RenameModel удалена. История локальной SQLite-базы синхронизирована с этой схемой без удаления записей. Не возвращать миграцию переименования.

Имена существующих полей и related_name пока не переименовывались: например, `membership`, `memberships`, `grants`, `system_grants`, `invitations` остаются в коде. Названия моделей во множественном числе сохранены по прямому запросу пользователя.

## Что уже реализовано

- Регистрация по email, имя и фамилия необязательны.
- Подтверждение email, вход/выход, восстановление и смена пароля.
- Серверные сессии, CSRF, ограничения частоты запросов в БД.
- Подача, одобрение и отклонение заявок на создание проектов.
- Карточка проекта и редактирование при наличии разрешения.
- Индивидуальный доступ участников, выдача и отзыв прав.
- Приглашения зарегистрированным пользователям по email, принятие, истечение срока и отзыв. Незарегистрированный email отклоняется до создания приглашения и отправки письма.
- Главный аккаунт назначает сотрудникам системные полномочия.
- Журнал действий.
- Системные полномочия, включая главный аккаунт, не дают автоматического доступа к клиентским проектам.
- Vue-интерфейс всех существующих сценариев: кабинет, проекты, команда, приглашения, системное управление и учетная запись.
- JSON API на существующих маршрутах через `Accept: application/json`; проверки прав, формы, сессии, CSRF и ограничения запросов остаются в Django.

В каталоге есть разрешения для будущих модулей. Сейчас из проектных действий реализовано только изменение сведений проекта. Финансов, мероприятий, договоров, подписей и грантовых заявок еще нет.

## Основные файлы

- `core/models.py`: модели и поля.
- `core/permissions.py`: каталог и проверки прав.
- `core/services.py`: транзакционные операции, подтверждение email и ограничения запросов.
- `core/views.py`, `config/urls.py`: сценарии и маршруты, общие для HTML и JSON.
- `core/frontend.py`: явная сериализация данных и форм, JSON-ошибки и редиректы, безопасные начальные данные Vue.
- `core/tests.py`: 30 тестов; `core/test_frontend.py`: 12 тестов JSON API; `core/test_browser.py`: опциональный браузерный прогон на отдельной тестовой БД.
- `frontend/`: Vue-компоненты и клиент API. `package.json`, `package-lock.json`, `vite.config.js`: зависимости и сборка.
- `frontend/views/`: отдельные представления; `frontend/pages.js`: реестр страниц; `frontend/composables/usePageNavigation.js`: навигация; `frontend/layouts/`: общая шапка. `App.vue` содержит только оболочку. Инструкция добавления страниц — `frontend/README.md`.
- `frontend/styles/`: компактный интерфейс со статическими стеклянными поверхностями. Размывание ограничено шапкой на широких экранах и отключается при уменьшении движения/прозрачности.
- `templates/app.html`, `static/frontend/`: оболочка и собранный Vue; остальные HTML-шаблоны — резервный интерфейс. Шаблоны писем продолжают использоваться Django.
- `config/settings.py`: конфигурация Django.
- `requirements.txt`: зависимости; локальное окружение `.venv`.
- `README.md`: запуск и ограничения.
- `BACKLOG.md`: ограничение приглашений зарегистрированными пользователями.

## Проверки и локальное окружение

После перехода на Vue прошли все 38 Django-тестов: 29 исходных, 8 проверок JSON API и 1 браузерный сценарий в Chromium. Также прошли 3 JavaScript-теста, сборка Vite и `manage.py check`. Тестовая БД создана с нуля. `makemigrations --check --dry-run` не обнаружил изменений. Мобильный интерфейс проверен по снимку браузера.

Проверки выполнялись на SQLite: PostgreSQL и Docker в доступном окружении не были найдены. PostgreSQL-конфигурация и compose.yaml подготовлены, но PostgreSQL не проверялся. Перед выпуском нужен прогон на PostgreSQL.

```sh
DEBUG=1 USE_SQLITE=1 .venv/bin/python manage.py check
DEBUG=1 USE_SQLITE=1 .venv/bin/python manage.py makemigrations --check --dry-run
DEBUG=1 USE_SQLITE=1 .venv/bin/python manage.py test
npm test
npm run build
# Браузерный прогон, после установки Chromium:
# npx playwright install chromium
DEBUG=1 USE_SQLITE=1 PROJECTUS_BROWSER_TESTS=1 .venv/bin/python manage.py test
```

Локальный сервер запускался на `127.0.0.1:8000` через инструменты Codex с `--noreload`. Перед новым запуском проверить, свободен ли порт; не запускать второй сервер на том же порту. Процесс может не сохраниться после смены чата.

В режиме DEBUG письма печатаются в вывод сервера, на реальную почту не отправляются. Не включать пароли, токены подтверждения или содержимое локальной БД в документы передачи контекста.

## Переход на Vue.js

Реализован Vue 3 + Vite. Публичные URL, серверные сессии и ссылки из писем сохранены. JSON API использует те же обработчики с заголовком `Accept: application/json`; POST отправляет обычные поля формы и `X-CSRFToken`. Пароли не возвращаются в данных форм. Модели и миграции не изменены, локальная пользовательская БД не использовалась для тестовых действий.

Перед запуском: `npm ci`, `npm run build`; при разработке компонентов: `npm run watch`. Сборка раздается Django из `static/frontend/`, в эксплуатации — через `collectstatic`. Подробный контракт JSON и команды проверок приведены в README.

Ограничение приглашений зарегистрированными пользователями реализовано. Ранее выданные приглашения сохраняются до истечения срока или отзыва; повторная отправка требует регистрации.

## Порядок дальнейшей работы

Главная `/` теперь показывает гостям публичный лендинг (`views.home`, `LandingView.vue`, резервный `landing.html`), а вошедшим пользователям — прежний защищенный dashboard. Имя маршрута `dashboard` сохранено для редиректов. Адаптер `page_data()` допускает явное имя Vue-страницы в серверном контексте `page`: для гостей это `landing`. На лендинге описаны существующие возможности; показатели, мероприятия, бюджет и договоры явно отмечены как разрабатываемые.

Добавлен пользовательский раздел «Мои договоры»: `/contracts/`, `views.my_contracts`, `MyContractsView.vue`. Пока это пустое состояние без модели и реальных договоров. Раздел доступен подтвержденному пользователю независимо от доступа к проектам; проектный sidebar здесь не отображается. Пользователь может быть стороной договора проекта, не являясь участником этого проекта. В будущем список должен включать все договоры на его имя из разных проектов. Детали модели и действий отложены, контекст сохранен в BACKLOG.md.

Внутри выбранного проекта добавлен sidebar: «Информация», «Показатели», «Мероприятия», «Бюджет», «Договоры». Компонент — `frontend/layouts/ProjectSidebar.vue`; он показывается, когда ответ сервера содержит `data.project`, включая формы редактирования проекта и прав участника. Контекст проекта определяется URL, сохраняется после обновления страницы и сбрасывается при выходе к списку проектов. На мобильных экранах меню раскрывается кнопкой.

Маршруты новых разделов: `projects/<uuid>/indicators/`, `events/`, `budget/`, `contracts/` (последние три также внутри `projects/<uuid>/`). Они используют `project_section` и проверку `accessible_project`; функционал пока не реализован. Будущее содержание разделов сохранено в BACKLOG.md. Новый Vue-шаблон заглушек — `ProjectSectionView.vue`.

При разделении Vue-представлений и уплотнении стилей проверены сборка Vite и один существующий браузерный сценарий на тестовой БД; просмотрены снимки входа, команды и кабинета на широком и мобильном экранах. Полный серверный набор повторно не запускался, backend не изменялся.

Пользователь самостоятельно анализирует архитектуру перед продолжением разработки. Проверки выполнять по затронутым сценариям, избегать повторных полных прогонов без необходимости. Обнаруженные ошибки и их исправления предварительно согласовывать с пользователем.

Выдача системных полномочий: `StaffPermissionsView.vue` использует `UserPicker.vue` и защищенный GET `/operations/staff/search/?q=...`. Поиск по имени, фамилии и email начинается от 3 символов с задержкой 300 мс и возвращает максимум 10 пользователей; устаревшие запросы отменяются. Логином остается email. Выбираются только активные подтвержденные учетные записи, кроме главного аккаунта. GET `/operations/staff/?user_id=...` загружает существующие полномочия, POST принимает `user_id` и `permissions`. Сервер повторно проверяет цель назначения под блокировкой в транзакции; аудит и отзыв пустым набором сохранены. Список сотрудников с назначениями разбит на страницы по 30 записей. HTML-fallback поддерживает поиск через GET-форму.

## Сведения проекта (7 октября 2026)

На вкладке «Информация» отображаются краткое описание, цели, задачи и начальная/конечная даты реализации. Блок «Ваш доступ» скрыт в Vue и HTML-fallback. Через существующее редактирование цели и задачи вводятся по одному пункту на строку; сохраняются упорядоченными списками в JSONField (`goals`, `tasks`). Даты необязательны, конечная дата не может предшествовать начальной. Добавлена и применена к локальной SQLite миграция `0002_project_information`; исходная миграция сохранена.

Проверены 13 тестов API, браузерный сценарий с новыми полями в установленном Chrome, 3 JS-теста, сборка Vite и отсутствие недостающих миграций. Для использования установленного Chrome в браузерных тестах: `PLAYWRIGHT_CHANNEL=chrome`. Скриншоты карточки — `test-results/project-information-desktop.png` и `test-results/project-information-mobile.png`.

Уточнение формы сведений: цели и задачи в Vue редактируются отдельными текстовыми полями. Кнопка «+» добавляет поле, «−» удаляет выбранное; минимум одно поле каждого типа остается всегда. Пустые пункты не сохраняются. API принимает повторяющиеся параметры `goals`/`tasks` и возвращает поля вида `text-list` с массивом значений. HTML-fallback без JavaScript сохраняет ввод списков по строкам. Браузерный тест проверяет добавление нескольких полей, удаление среднего пункта, запрет удаления последнего поля и отображение сохраненных сведений после перезагрузки.

## Показатели проекта (7 октября 2026)

Реализован раздел «Показатели»: список, создание и редактирование качественных и количественных показателей. Модель `ProjectIndicator`, миграция `0003_project_indicators` применена к локальной SQLite. Качественный показатель содержит текст формулировки, текущий результат и отметку «Достигнут». Количественный — формулировку, положительную десятичную цель (до 3 знаков после запятой), необязательную единицу измерения и `current_value` (начально 0, не редактируется пользовательской формой). Показываются факт/цель, процент и прогресс; процент может превышать 100%. Тип фиксируется после создания. Просмотр — участникам проекта, управление — владельцу и участникам с `EDIT_PROJECT`. Создание/изменение записываются в аудит.

Мероприятия пока не реализованы: автоматического накопления факта сейчас нет. При разработке мероприятий связать их вклад с показателями и обеспечить атомарный перерасчёт `current_value` при создании/изменении/удалении результатов, защиту от повторного начисления и проверку принадлежности одному проекту. Форма определения показателя обновляет только свои поля, чтобы не перезаписать будущие параллельные начисления.

Маршруты: `project_indicators`, `indicator_create`, `indicator_edit`. Vue: `IndicatorsView.vue`, `IndicatorFormView.vue`; HTML-fallback: `indicators.html` и общая форма. Проверены 17 серверных тестов (API и показатели), браузерный сценарий создания обоих типов и изменения результата, сборка Vite. Снимки: `test-results/indicators-desktop.png`, `test-results/indicators-mobile.png`.

## Мероприятия (7 октября 2026)

Реализованы плановые мероприятия и факт проведения, подтверждение, приватные фотографии/файлы. Модели `ProjectEvent`, `EventIndicator`, `EventAttachment`; миграция `0004_project_events` применена к локальной SQLite. Код разделён на `core/event_forms.py`, `core/event_views.py`, `core/event_services.py`, `core/event_data.py`. Vue: `EventsView.vue`, `EventDetailView.vue`; формы плана/факта используют `PageForm` с условными числовыми полями. HTML-fallback также реализован.

План: название, начальная/конечная дата, ожидаемый результат, задачи проекта, показатели. Задачи пока хранятся в Project как JSON-строки, поэтому выбранные формулировки сохраняются в плане снимком; изменение списка задач проекта не стирает их из ранее созданного мероприятия. Качественные показатели привязываются справочно; количественные — с неотрицательным плановым значением (до 3 знаков после запятой). Факт: фактические даты, результат, обязательные значения всех количественных показателей, включая явный ноль. План и факт сравниваются в карточке.

Статусы: planned → conducted → confirmed. До подтверждения план и факт можно изменять раздельными разрешениями; уже заполненный количественный факт нельзя потерять отвязкой показателя из формы плана. Новому показателю в проведённом мероприятии потребуется внести факт перед подтверждением. После подтверждения все формы изменения и операции с вложениями запрещены даже владельцу. Подтверждение повторно не начисляет значения. Сумма `ProjectIndicator.current_value` пересчитывается из фактов подтверждённых мероприятий в транзакции с блокировкой мероприятия и показателей в стабильном порядке. Качественные показатели при этом автоматически не меняются. Текстовое сравнение ожидаемого/фактического результата остаётся на усмотрение пользователя.

Права: существующий `EDIT_EVENTS` теперь «Создавать и редактировать плановые мероприятия»; новые `EDIT_EVENT_RESULTS` и `CONFIRM_EVENTS` независимы. Просмотр требует `VIEW_EVENTS` либо одного из трёх разрешений на действия; владелец имеет все. Новые разрешения автоматически доступны в настройках участника и приглашении. Системные полномочия не открывают чужие мероприятия.

Вложения доступны после внесения факта и до подтверждения. Типы: фотографии, списки участников, организационные документы, приказы, программа, отчёты/отзывы, другое (по умолчанию). До 20 МБ на файл. Хранение: `private_uploads/`, случайные имена; публичные media-маршруты не добавлены. Скачивание — только защищённый маршрут с проверкой проекта/прав, как attachment, с nosniff и no-store. Не настраивать публичную раздачу private_uploads. До подтверждения разрешено удалять файл; после — только скачивание. Frontend API автоматически переключается на multipart при наличии File/Blob. Все изменения и подтверждение записываются в аудит.

Проверки на SQLite: 25 серверных тестов по событиям, API и показателям плюс браузерный сценарий в Chrome; 4 JS-теста, Vite build, проверка миграций. Проверены роли, межпроектная изоляция, CSRF, даты, значения, загрузка/скачивание/удаление файлов, блокировка, повторное подтверждение, сумма нескольких мероприятий и откат при переполнении. Браузерные тесты используют временную папку вложений и отдельную тестовую БД. Конкурентное поведение под PostgreSQL ещё не проверялось.
